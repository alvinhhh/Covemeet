## Durable phone journal follow-up

The native supervisor now persists a capacity reservation before answering or entering IVR. It records owner/process and PBX labels, exact scoped identifiers, allocation/playback intents and outcomes; entered PINs, caller numbers and meeting session capabilities are excluded. Application join atomically binds the meeting participant to its journal, so a lost join response does not prevent call-ID-based revocation. Clients validate bounded responses, pin immutable ownership fields and refresh the expected revision before writes.

Only the current owner can stop and finish its journal. Stopping revokes the bound participant before teardown; an authority failure still permits best-effort native cleanup and withholds release. Ordinary `leave` cannot release a journaled reservation. The trusted current supervisor submits finish proof after verifying closure of the caller, outbound leg, bridge, native peer, holding relay and RTC paths. The API checks ownership, revision, complete proof and the absence of pending/unknown/sticky-uncertain operations; it does not independently inspect the PBX. Phone disable prevents new admission/intents while keeping authenticated journal query/stop/finish and existing-call `leave` available.

The ownership review found that a deterministic resource name alone could cause cleanup to delete a colliding channel or bridge. The adapter now records confirmed creation separately for each resource, preserves `409`/unowned resources, removes only owned native peers matching the configured identity/trunk/rule, and requires all holding peers to be absent before completion. Callback checks after durable intent acknowledgment also prevent answer, playback, originate, bridge creation or attachment after local termination. Focused tests cover these races, known rejection versus unknown outcomes, lost join/create/settlement responses, owner substitution and cleanup failures.

Unknown outcomes remain sticky: an immediate absent lookup, restarted process or new PBX epoch cannot prove that a delayed allocation will not finish. PBX startup now uses an atomic non-expiring claim, checked in the same transaction as reservation, join and allocation intents. A separate single-host Docker manager persists fencing, verifies the original daemon and exact managed container labels/IDs, disables restart and removes the original supervisor/PBX/SIP. Recovery verifies fresh container IDs and a new PBX boot digest, revokes bound meeting access and reconciles only exact recorded native SID bindings. Ownership transfers only after all old journals close. Unknown/pending work, peer collisions or unverifiable cleanup remain reserved; no timeout or API takeover route bypasses this. The current local native run (5 October 2026, 05:21:43–05:24:49 UTC) passed all 18 ordinary checks, actual admitted-orphan fencing/reconciliation and four fresh native call checks. The fence retained capacity; confirmed reconciliation released it and installed the fresh boot owner. All outer cleanup flags passed. A five-second relay-departure observation originally failed against the pinned SFU’s normal failure timers; the bounded 30-second observation now passes without deleting an unrecorded relay SID. Fixed stage labels and journal state/counts identify failures without raw provider exceptions or private bindings. Multi-host takeover is unsupported. The unjournaled call-file CLI remains test-only.

## Phone foundation follow-up

An independent code review of the experimental phone admission, host controls and isolated audio relay found a terminal-cleanup race: a delayed RTC connection or publication could finish after cleanup, and a failed teardown could lose its resource reference. The relay now serializes opening and closing, checks terminal state after asynchronous operations, retains failed legs, and waits for pending SDK work before acknowledging cleanup. A follow-up also found that failed initial holding setup could lose its cleanup evidence; opening errors now retain their bridge, and unknown cleanup outcomes withhold the reservation release. The 26 phone tests include deferred lifecycle and failed-opening regressions. This follow-up was not performed by Daybreak and does not extend the earlier review to a native SIP implementation.

The final isolated PostgreSQL/LiveKit fixture passed eight audio/admission checks, including silence before admission, default mute, keypad controls, host mute enforcement, and reservation release only after both media legs and the simulated native participant are gone. The database test exercised two API instances sharing the same call cap. The fixture used an RTC peer in place of SIP; no carrier, TLS/SRTP trunk negotiation, IVR, or production load was tested.

The requested Ponytail pass removed an unused phone-access version counter; admission still checks the current locator and PIN hash. Phone access stays disabled by default. See [phone/SIP gates](phone-sip-design.md#gates-before-real-dial-in) for the native call control, announcements, encryption negotiation, orphan reconciliation and capacity work still required.

## Earlier Daybreak review

Daybreak reviewed the API, recording library, hosted adapter, and tests during implementation. It found no direct host/guest privilege escalation or recording cryptography break, but requested changes. This review is not an audit or a certification.

The implemented responses are:

- Preserve and reconcile recorder identity after post-start failures; request recorder shutdown rather than incorrectly marking an active recorder failed.
- Enforce participant expiry on established signaling connections and retry removal through the application worker.
- Authenticate the host before looking up a recording token in its specified meeting, avoiding unauthenticated whole-database token searches.
- Keep download capabilities in URL fragments, clear them before rendering, and submit them in a request body.
- Bind public signaling to the participant's host-only meeting cookie as well as its short-lived media token. Serialize signaling messages so database checks cannot reorder them.
- Require TLS for production password email. The hosted adapter requires HTTPS for non-loopback upstreams and includes its credential only on privileged mutations.

WebRTC signaling still uses the SDK's token query parameter. The reverse-proxy template disables access logging; deployments must preserve that rule or redact the complete query. Cookie binding reduces replay through the public gateway, but it does not replace private raw-SFU isolation. The older development stack deliberately exposes raw signaling on loopback; the isolated TLS stack has no raw signaling host publication and passed the local bridge probes above. External host/firewall isolation, concurrent hostile reconnect under dependency failures and the other deployment gates remain open.

The core and hosted service currently implement one configured installation. The 100-person and 1,000-viewer limits are targets pending load tests. Production phone/carrier readiness, shared multi-tenant provisioning, subscriptions, high availability, end-to-end media encryption, and operating evidence for compliance remain later work.
