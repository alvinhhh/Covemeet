# Initial API contract

Same-origin `/api`, JSON. Mutation calls send `Content-Type: application/json` and `X-Requested-With: MeetingPlatform` (the stable protocol marker). The recording attachment route also accepts a native form POST as described below. Cookie-backed HTTP-only sessions. Errors `{error: string}`. All GETs no-store. No client-supplied tenant. Single installation/tenant for this first implementation.

- `GET /api/config` → `{edition:'hosted'|'self-hosted',brandName,recordingAvailable,mediaAvailable,creationRequiresKey}`.
- `POST /api/meetings` body `{title,hostName,password,mode:'meeting'|'webinar',customCode?,creationKey?}` → `{code,hostToken,guestUrl}`. Never persist plaintext hostToken in local storage. Navigate `/host/CODE#TOKEN` and immediately exchange/clear fragment.
- `POST /api/meetings/:code/host` `{token}` → `{participantId}` + session cookie. Token single use.
- `POST /api/meetings/:code/join` `{name,password}` → `{participantId}` + session cookie; lobby by default.
- `GET /api/meetings/:code/state` → `{meeting:{code,title,mode,locked,ended,recordingAllowed,chatMode,createdAt},me:{id,name,role,status,audioAllowed,videoAllowed},participants:[{id,name,role,status,audioAllowed,videoAllowed}],messages:[{id,name,text,createdAt,sequence?,recipientId?,deleted?}],recordings:[{id,status,createdAt,expiresAt?}],revision}`. Guests see admitted participants and themselves; hosts also see waiting/rejected/kicked/banned. Status waiting/admitted/kicked/banned/left. Role host/participant/viewer.
- Poll state every 2s; 401/403 means show a join page, never silently create a new session.
- `POST /api/meetings/:code/participants/:id/action` `{action:'admit'|'kick'|'ban'|'allow-audio'|'block-audio'|'allow-video'|'block-video'|'promote'|'demote',banIp?:boolean,banDevice?:boolean}` → `{ok:true}`.
- `PATCH /api/meetings/:code` `{locked?:boolean,recordingAllowed?:boolean,chatMode?:'everyone'|'host-only'|'disabled'}` → `{ok:true}`; host only.
- `POST /api/meetings/:code/end` `{}` → `{ok:true,cleanupPending}`. Returns 202 while media, phone or recorder cleanup is unresolved; 200 after confirmation. State polling exposes `meeting.cleanupPending` until cleanup finishes.
- `POST /api/meetings/:code/leave` `{}` → `{ok:true}` for a guest. Host leave ends the meeting for everyone and returns `{ok:true,cleanupPending}` with 202 while cleanup is unresolved.
- `POST /api/meetings/:code/messages` `{text,recipient?:'everyone'|'host'|participantId}` → `{ok:true}`. Public messages stay in the current breakout; private messages are guest-to-host or host-to-admitted-browser-guest. Sender policy is enforced on this endpoint and host-only `/broadcast`. `DELETE /api/meetings/:code/messages/:messageId` removes text and retains a tombstone; host only. See [Chat](chat.md) for visibility and retention.
- `POST /api/meetings/:code/media` `{}` → `{token,url,mediaIdentity}`; only admitted sessions. URL is the gateway signaling endpoint. Client uses `autoSubscribe:false` and explicitly subscribes to admitted participants' audio and at most 16 visible video tiles including local video. Screen shares receive bounded priority; remaining tiles are paginated. Webinar video excludes audience placeholders. Camera and microphone start off.
- `POST /api/meetings/:code/host-email` `{email}` → `{ok:true}` sends OTP. `POST /api/meetings/:code/verify-email` `{otp}` → `{ok:true}`.
- `POST /api/meetings/:code/recordings` `{}` starts optional recording if available, allowed and host email verified. `POST /api/meetings/:code/recordings/:id/stop` `{}` stops. Completion automatically creates one 24-hour link intent and emails only its password to the verified room address. Authenticated host `GET /api/meetings/:code/recordings/:id/link` → `{url,expiresAt}` retrieves the current link with `Cache-Control: no-store`; it never returns the password. Host `POST` to the same path `{}` replaces the pair and emails the new password. `POST /api/meetings/:code/recordings/:id/revoke` `{}` revokes.
- `/download/:code#token` UI accepts password; `POST /api/meetings/:code/download` `{token,password}` returns decrypted media as attachment, requires host session. The UI uses a native URL-encoded form POST to stream the attachment to the browser without buffering the file in JavaScript. Only this route accepts that form type without the custom header, and only with the exact configured meeting `Origin`. Duplicate/unknown fields, missing/cross-origin requests and non-host sessions are rejected. Token and password stay in the POST body; the fragment is removed before rendering. The page uses `Referrer-Policy: same-origin`: other origins receive no referrer, and native form POSTs retain the same-origin `Origin` header. `no-referrer` would make that header `null` under the [Fetch origin algorithm](https://fetch.spec.whatwg.org/#append-a-request-origin-header); null origins remain rejected. The response frame permits forms and downloads but no scripts. Failed form requests retain their HTTP status and return escaped JSON inside a script-free HTML document, so the frame can display the error; JSON API callers still receive JSON.

Meeting state also includes `participantLimit`, optional `startedAt` and `deadlineAt` (epoch milliseconds). The fixed session clock starts on the first host entry. Reconnecting or refreshing a paid entitlement does not extend it. Finished recording downloads remain available after an ordinary meeting end; revoking the host account removes that access too.

Each participant in `me` and `participants` has a logical `id`, a `mediaVersion` and a current `mediaIdentity`. Use the logical ID for host actions, chat, room assignments and usage. Use `mediaIdentity` to match SDK participants, tracks, names and speaking indicators. A permission or removal fence rotates the media identity with the version and retains the retired identity until cleanup is confirmed. Delayed cleanup targets that retired identity. Phone grants use physical media identities in `subscribeParticipantIds`; phone dialog and participant IDs remain logical.

Unmetered gateways persist a connection ID and a 15-second presence deadline before opening upstream signaling. Only the current connection can renew that deadline or start cleanup. The existing worker fences expired connections and retries removal; logical admission stays available for reconnect after cleanup. Hosted gateways use the participant meter's existing presence rule. Database or SFU outages can delay confirmed physical removal.

Deploy the API and matching browser bundle together, stop older gateway processes and reload older browser tabs. Persisted participants without `mediaIdentity` retain their logical ID as their media identity until their next fence; clients must only use that fallback when the field is absent.

Expired, departed browser guests can be removed from the meeting document once media cleanup is complete, but only when `auditReferenced` is explicitly `false`. New guest joins set that marker; moderation sets it to `true` in the same transaction as the action, before its audit event is written. Legacy rows without the marker, audited guests, hosts, phone participants and unresolved cleanup remain. All API writers sharing a store must upgrade together: older writers do not maintain the marker. A rollback must invalidate these cleanup markers before older writers resume; do not backfill legacy rows as unaudited. This cleanup does not bound audited history or the 12-hour session window.

The hosted adapter uses authenticated private endpoints for account authority, named host entitlements and meeting creation. Entitlements carry a monotonic revision, a short expiry and the allowed hosts for one billing owner. New customer meetings require a current grant; self-hosted installations do not require subscriptions. Personal grants allow 100 people, two hours and one active meeting. Teams grants allow 100-person meetings, webinars with 1,000 viewers plus ten stage members, eight hours and one simultaneous meeting per paid seat (maximum 100). Every named host still has at most one active meeting. Capacity remains reserved until cleanup is confirmed.

`POST /api/internal/hosted/meetings/status` accepts `{accountId,version}` with private machine authentication and returns `{meetings:[{code,status}]}` for that account's started rooms that still hold a reservation. The requested account version may be newer than the room's version after account recovery, but never older. Status is `active`, `orphaned` when the host explicitly left, or `ending` while the room is closing. `POST /api/internal/hosted/meetings/:code/end` accepts `{accountId,version}` and ends any started room bound to that account; the same owner can retry cleanup for an already-ended room. It returns `{ok:true,cleanupPending}` with 202 until cleanup is confirmed. Guests may still be connected when the owner explicitly ends the room. Closing a room does not require a current paid grant. Both endpoints reject browser credentials.

Hosted grants also carry `quota:{anchorAt,metering?,participantSecondsPerMonth,recordingSecondsPerMonth?,downloadBytesPerMonth?,storageBytes?}`. An enabled grant requires a quota; a disabled grant may carry `null`, which does not erase earlier usage. The first paid UTC anniversary is permanent for the billing owner. Monthly boundaries clamp that original day in shorter months: January 31 resets on February 28 or 29, then March 31. Changing the subscription, seats or grant revision does not reset usage.

New paid grants set `metering:"meeting"` and `participantSecondsPerMonth:null`: there is no cumulative monthly meeting-time cap. Older numeric grants retain their limit until a newer grant arrives. A meeting has one atomic 30-second reservation shared by every attendee, phone leg and breakout; concurrent meetings consume separate intervals. Counting starts at the first successful upstream signaling connection and includes setup, quiet time and presence/reconnect grace. A never-opened meeting uses zero. Presence renews the interval; admitted rows alone do not. Unknown cleanup retains the control reservation and blocks new allocations, while already-funded access can finish. Uncapped time still uses short control leases bounded by paid authority and the fixed session deadline; it does not authorize indefinite disconnected or unpaid access.

Older grants without `metering` retain participant counting. The first meeting-mode revision drains existing funded legacy rooms and pins a separate meeting-time counter; historical participant usage is preserved, never relabeled. New revisions cannot switch that owner back. Upgrade all API workers together and verify no active legacy sessions before refreshing grants. Unbound legacy and self-hosted rooms are unchanged.

`POST /api/internal/hosted/usage` accepts `{billingOwnerId}` with the same private machine authentication as other hosted controls. It returns `{ok:true,metering:"participant"|"meeting",window:{start,end},participantSeconds:{limit,used,reserved,available},recordingSeconds:null|{limit,used,reserved,available},recordingDownloadBytes:{limit,used,available},recordingStorageBytes:{limit,used,reserved,available},asOf,blocked}`. Times are epoch milliseconds; time counters are integer seconds and byte counters are integers. The retained `participantSeconds` field follows `metering`; clients must label it accordingly. Its `limit` and `available` are both `null` for uncapped time, while `used` and `reserved` remain integer counters. Missing fields are not uncapped permission. `recordingSeconds:null` means the current grant has no monthly recording-time cap, not an unknown balance. Used and reserved time round up; available time rounds down from the stored millisecond amounts. Clients must not recalculate available time from the rounded display counters. Missing paid usage history returns 404 with code `USAGE_UNAVAILABLE`; connection or storage failures are not an empty balance. Hosts receive the same aggregate in `meeting.usage`; guests do not. The hosted portal resolves the billing owner from the signed-in account and rechecks membership before returning the aggregate.

A bound recording reserves time under its original billing owner's lock before starting Egress. Missing `recordingSecondsPerMonth` means zero; explicit `null` removes the monthly recording-time cap. New paid plans use `null`, hosted capture requests 1280×720 at 24 fps, and new starts still require a current enabled grant plus storage capacity. Seven-day retention and the meeting deadline remain enforced. The entire elapsed interval plus prepaid time remains reserved while the job is unresolved. Provisional start timestamps may change; the earliest observed start keeps the hold conservative. Only matching terminal Egress proof settles job time once, using top-level `startedAt` and `endedAt`, including recorder startup and shutdown rather than MP4 duration. Time crossing a monthly boundary is split across the original owner's fixed windows. Unknown starts, missing jobs and failed stop requests retain their holds and block further recording allocations; they are not refunds. Unbound self-hosted and legacy rooms keep their existing recording behavior.

A hosted recording download debits its full declared plaintext size atomically against the meeting’s original billing owner before any plaintext is returned. Retries count again; canceled or interrupted downloads receive no refund. Wrong credentials, an unreadable initial ciphertext frame, or failed current-host authorization consume no allowance. The decryptor authenticates each frame and rejects bytes beyond the declared size before emitting them; complete-file integrity is verified at EOF. Closing the HTTP connection during preparation cancels pending storage reads and denies admission before debit. A disconnect after admission retains its debit. Download usage has no reserved counter and does not consume meeting time.

Download allowance uses the same monthly window as meeting usage. Missing `downloadBytesPerMonth` means zero for old bound grants; a newer grant must supply it before positive-size downloads. Ordinary meeting end, hosting-lease expiry and cancellation preserve download access within retention and the retained allowance. Revoked accounts/recordings still fail. Explicitly unbound legacy and self-hosted rooms have no hosted quota. Authorization, link expiry, the seven-day retention deadline, recording metadata and available allowance are rechecked together at admission, then current authority is checked before each plaintext frame. Revocation or expiry stops later frames; bytes already released cannot be recalled.

These allowances do not invoice overages or establish a bandwidth/spending cap. If SFU control is unavailable, signaling denial alone cannot guarantee that an existing direct media connection has stopped. Unconfirmed cleanup retains its reservation and blocks new allocations. The installed Egress API has no per-job duration cap; worker or control-plane outages can overrun a recording reservation before stopping is possible. Storage capacity remains enforced independently. The earlier capped recording-time source checks and six-phase real-recorder runtime fixture passed; the new uncapped policy requires its own rebuilt runtime evidence. The observed shutdown overran its funded deadline; see the requirements ledger for counts and scope.

Phone integration and 100/1000 media capacity require separate runtime validation.
