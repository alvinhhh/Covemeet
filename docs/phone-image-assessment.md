# Native phone image assessments

These decisions cover the configured SIP and Asterisk services in the Linux/amd64 native-phone validation. They do not assess the Node phone worker, carrier behavior, or host operator commands. The [SIP](../security/sip-image.vex.json) and [Asterisk](../security/asterisk-image.vex.json) OpenVEX files record each of the 14 reviewed advisories separately; neither file says the matched Debian package is patched.

## SIP

The inspected SIP image is `sha256:69978cdd526b933580636f1b4c1217abcd14a4f2a2905e7153a73a6874515887`, built from revision `74dd2795b0d818e47b8b748d748d17ff13f0cfa0`. Its Dockerfile and entrypoint match that source. The prior configured image `sha256:9092356d5e2ac14abada81563a12be7f485296b3cd41cf33229598ec8b257f4c` was assessed independently; comparing stopped containers showed the same `livekit-sip` executable (`c47fce23b7bda1b4267ec981ab247b9e8cc44c98407ad3512f5cd9a125e06b35`), entrypoint (`a90205500fbd60bed950af82c7d798853365898b863efd132fa6259bf1e14a86`), libc, libz, and libstdc++ bytes. The new image changes OpenSSL from `3.5.7-1~deb13u2` to `3.5.7-1~deb13u3` and PCRE2 from `10.46-1~deb13u2` to `10.46-1~deb13u3`; the Dockerfile enforces these minimum versions.

The executable still links directly to libsoxr, libopus, libopusfile, and libc. Its exact undefined symbols do not name the affected resolver printers, monetary formatter, gz writer, or ACL file APIs. The entrypoint rejects plaintext SIP port 5060 in its own network namespace, then drops all capability sets and enables no-new-privileges before starting the service. The installed mount/nsenter, infocmp, ACL, and Perl tools are not invoked by this configured path. A compromised SIP process can still access its own SIP credentials and TLS key; these VEX decisions do not remove that risk.

The updated OpenSSL, crypto and PCRE2 library hashes are `9592038e92d1f41affcbb625334d0b6e788714c889104fa6d5b107cf9fd657f2`, `8ae56f0a9481280a68c19f59809cd242a07a91ad7142944d21a878221992244b`, and `92e9b4167f9bbc237ca8f5526d82ee99ec9f8dbd0270ef1dd0ab24e2217f48e3`. CI checks those bytes, the executable and entrypoint, libc/libz/libstdc++, package inventory, source inputs, and launch configuration before applying SIP VEX. A different image is scanned unfiltered and fails pending review.

## Asterisk

The reviewed cached image is `sha256:0d9bf9da1a52d79be46ad58cdddbbfda84985285caf4e3381fec30959fb439f3`, built from revision `afed38196e1e469e10e77017201276db9264b0d8`. The Asterisk Dockerfile and configuration inputs are unchanged through revision `74dd2795b0d818e47b8b748d748d17ff13f0cfa0`; that does **not** establish that a new build has identical native bytes. The reviewed executable hash is `0c3b33cefbddaa9fce2f20c6a97f655e997960406ae1e9d29f29f4d931b5237f`; direct support libraries `libasteriskssl.so.1` and `libasteriskpj.so.2` hash to `3fd6eb6dabc170527b79cfcf67b0097bc7beef8cd6f98f1866323750ae496520` and `6f6a1356880c1b3b8bcf18a47954e1ade48a1014fea60568f11d8db5fcac9aff`. The 304 installed modules have a sorted path-and-SHA-256 manifest digest of `3b746d9d4511180079b186fa8adce061b4ca8038bafe7229d04460384850901f`.

The inspected executable, modules, and support libraries have no caller for the affected GNU PBDS heap, deprecated resolver printers, monetary formatter, or gz writer paths. The exact libstdc++ aligned allocation uses `posix_memalign` without the vulnerable rounding branch. The configured service starts Asterisk directly as UID 10001 with all capabilities dropped and no-new-privileges; it does not run mount/nsenter, ACL CLI, infocmp, or Perl modules on supplied input.

Asterisk 22.11.0 generates `build.h` from the UTC clock, host name, kernel and user. That header is linked into `/usr/sbin/asterisk` and `func_version.so`, so their full hashes can change on an otherwise identical build. CI pins the source archive checksum and build recipe, checks all 304 module names, hashes the other 303 modules and support/runtime libraries, and checks package inventory and launch configuration. For the two date-bearing ELF files, it checks architecture plus imports and dependencies for the affected native paths. New or changed native callers, source, libraries, modules or packages block the assessment; a different build timestamp does not. The build compiler and those two full ELF hashes are not independently pinned. No second Asterisk image was built for this assessment.
