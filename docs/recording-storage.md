# Recording keys, object storage, and recovery

The application supports its existing local encrypted files, a rotating local keyring, AWS KMS envelope wrapping, and private S3-compatible ciphertext storage. Existing `operator-kek-v1` envelopes remain readable with the original `RECORDING_KEK`. These adapters do not establish FIPS validation, media E2EE, production readiness, or compliance.

New hosted recordings stamp context version 2 at reservation and authenticate the creation-time billing owner in their encryption, key envelopes, object references, and links. Missing markers on older recordings and version 1 self-hosted recordings retain the `installation` context. An invalid or missing owner on a version 2 row, or an unsupported version, fails closed. This tenant binding does not provide separate per-tenant KEKs, KMS keys, S3 identities, or database isolation. Upgrade all API workers together before creating version 2 recordings.

Recording starts only after the host enables recording and verifies an email address. The recorder is a trusted participant that can access plaintext media. Keep its raw spool on bounded tmpfs or an encrypted ephemeral volume, with encrypted/disabled swap and restricted access. The encryption package authenticates each chunk with AES-256-GCM and a separate per-recording data key before storage. It cannot retroactively secure a raw file already written to a durable unencrypted filesystem.

## Hosted recording time

Bound hosted recordings reserve from `recordingSecondsPerMonth` under the original billing owner's lock before Egress starts. Old grants without the field provide zero recording time; numeric grants retain their cap. New paid plans use explicit `null`, removing the monthly recording-time cap while preserving bounded control leases, exact job ownership and uncertain-job holds. Usage returns `recordingSeconds:null` for that policy. Hosted capture requests 1280×720 at 24 fps; self-hosted encoding defaults are unchanged. Seven-day retention and the active meeting deadline still apply. A new recording requires a fresh enabled grant; self-hosted and explicitly unbound legacy rooms do not require a subscription. The allowance shares the owner's immutable UTC monthly anniversary with meeting and download usage.

Upgrade all API workers before enabling the new hosted grants; older workers do not enforce recording-time reservations. Existing bound recordings without a reservation are stopped and retain their uncertain time until terminal evidence is recovered.

The whole unresolved elapsed interval plus prepaid time stays reserved. Only exact terminal Egress proof debits once, using the job's top-level `startedAt` through `endedAt`, including startup and shutdown rather than the MP4 duration. Pinned Egress v1.14.1 initializes job timing in [pipeline configuration](https://raw.githubusercontent.com/livekit/egress/v1.14.1/pkg/config/pipeline.go) and maintains separate file timestamps and duration in its [controller](https://raw.githubusercontent.com/livekit/egress/v1.14.1/pkg/pipeline/controller.go). A job crossing a monthly boundary is split across the original owner's windows. A lost start response, absent lookup, failed stop or uncertain job identity retains its hold and blocks new recording allocation; none proves unused time can be refunded.

Egress v1.14.1 returns a provisional start time from [request validation](https://github.com/livekit/egress/blob/v1.14.1/pkg/server/server_rpc.go#L64), then [initializes the same job again in its child process](https://github.com/livekit/egress/blob/v1.14.1/cmd/server/main.go#L167). Both paths call [the timestamp initializer](https://github.com/livekit/egress/blob/v1.14.1/pkg/config/pipeline.go#L184), so a later observation can legitimately have a different start time. Unsettled reservations retain the earliest observed start and do not release held time when that value changes. The first valid terminal interval for the exact job determines the debit; its persisted interval rejects conflicting later terminal evidence.

The five-second capture/control pass is separate from a single-flight file-finalization pass. Slow encryption or upload therefore does not hold up stop checks for other active jobs; both passes retain per-recording database ownership. The installed Egress API offers no per-job duration cap. Worker, database or Egress control outages can overrun the funded interval, so this is not a hard infrastructure-spend cap. Recording-time typecheck/build and source tests passed; the requirements ledger records the focused and isolated PostgreSQL checks.

The earlier capped-policy runtime validation on 2026-10-05 used two silent video peers, normal host email verification and recording opt-in, and a fresh 60-second owner allowance. Egress stopped automatically after funding expired: its final job interval was 62.680 seconds, shown as 63 used seconds, with no remaining reservation. Completion was 2.746 seconds after the funded deadline; this overrun was charged rather than hidden. Terminal replay did not charge twice, encryption completed, and a second start returned `409`. Independent cleanup checks found no fixture database rows, files, mail, or live participants for either the initial failed timestamp fixture or the corrected run. Both exact recorder jobs were terminal.

## Hosted stored-recording allowance

New bound recordings reserve encrypted storage alongside recording time, before Egress starts, under the original billing owner's lock and the already-reserved database connection. `quota.storageBytes` supplies current capacity; an omitted field means zero. Personal supplies 5,000,000,000 bytes; Teams supplies 10,000,000,000 bytes per confirmed paid seat. Download allowance is separately 20,000,000,000 bytes per paid seat per month. This capacity does not reset monthly or move when the host changes teams. Downgrades block new allocations without deleting existing recordings.

Each capture reserves one local copy, or two copies when S3 also needs a local recovery file. Each copy's ceiling is the smaller of 3 GB, `RECORDING_MAX_BYTES`, and remaining capacity divided by the number of copies. This conservative reservation can serialize captures. The control pass requests stop at 90% of the ciphertext ceiling; the encoder separately enforces the exact ceiling, including framing. If recorder shutdown overshoots it, the oversized raw output is removed after terminal confirmation and is not published.

Every local or S3 attempt has a durable immutable identity before it can write. Unknown attempts retain their full ceiling; verified closed files or retained object versions count their actual ciphertext bytes. Local cleanup requires a receipt bound to the prepared metadata and path, plus confirmed removal of final and partial files. The permanent `.closed` marker remains to prevent a delayed invocation reopening a released attempt. Envelope rotation preserves the original prepared metadata needed to verify that receipt. A missing/pending receipt, lost database session, absent file, or expired grant does not release capacity.

The paid S3 path uses a conditional single PUT, at most 3 GB per object, and requires bucket versioning. It persists the exact destination identity, key, size and digest before sending; retries recover or conditionally replay that same intent. Cleanup installs a retained zero-byte fence, verifies and removes the exact key's owned data versions, and confirms that only the fence remains before release. Missing objects, delete markers and lifecycle expiry are not cleanup proof. Seven-day retention keeps the recording in `deleting` with its attempt evidence until every copy is settled.

`recordingStorageBytes` reports integer `limit`, `used`, `reserved` and `available` bytes; available is `max(0, limit-used-reserved)`. This measures managed ciphertext copies, not total physical disk use: raw spools, in-flight downloads and open-file reclamation, permanent `.closed`/zero-byte control markers, provider reclamation delays, replicas and independent backups need separate capacity and retention controls. Unknown local pending attempts require verified writer-fencing recovery; a missing receipt is never enough to release them.

Upgrade all API workers together. Any bound recording history without attempt inventory blocks new paid captures and reports storage usage unavailable, even if the old row says deleted. Reconcile that owner's existing files, objects and abandoned attempts before an explicit inventory migration; there is no automatic zero backfill. Existing authorized downloads and legacy retention remain available. Self-hosted and deliberately unbound rooms keep their existing storage path.

Focused tests cover quota races, unknown holds, restart, downgrade, month rollover, exact evidence binding, lost metadata/upload acknowledgements, key rotation, failed cleanup and capture overshoot. The current source passed eight storage-ledger tests, 29 recording-start tests, 42 existing recording-service tests and ten isolated PostgreSQL cases. The versioned local MinIO fixture also passed native PUT/replay, retained-fence cleanup, old-version denial and rejection of a delayed real conditional PUT; its generated bucket and containers were removed. The complete core typecheck, build and regression suite passed: 382 tests with 14 opt-in skips. Rebuilt-runtime validation and CI for this storage change are pending.

## Local keys and rotation

`RECORDING_KEY_PROVIDER=local` is the default. `RECORDING_KEK` supplies the legacy 32-byte base64 key under `RECORDING_KEK_ID` (default `operator-kek-v1`). Additional keys come from `RECORDING_LOCAL_KEYS`, a secret-manager-injected JSON object mapping key IDs to canonical base64 32-byte values. `RECORDING_ACTIVE_KEY_ID` chooses the key for new recordings and rewrapping. Do not place real keyring values in Git, browser fields, command arguments, screenshots, or logs.

To rotate safely:

1. Back up the database envelopes, object references, and ciphertext. Preserve wrapping keys separately under restricted operator access. A ciphertext backup without its exact envelope and recoverable wrapping key cannot be restored.
2. Add a new key to the keyring while retaining every key needed by live recordings and retained backups. Set its ID as active and restart the service. New recordings now use it; older recordings remain readable.
3. Call `POST /api/admin/meetings/:code/recordings/:id/rotate-key` through an authenticated operator session with the required mutation-origin/header protections. It accepts no caller-selected key. Ordinary meeting hosts and guests cannot rotate wrapping keys. The configured active key is the only target.
4. The service unwraps the existing data key, wraps it under the active key, verifies the entire recording through authenticated decryption, and atomically replaces unchanged database metadata. Ciphertext bytes, object key/version, tenant/meeting/recording binding, and recording data-key ID remain unchanged. A verification or concurrent-update failure keeps the prior envelope.
5. Restore and decrypt a backup using the retained key configuration before retiring any key. Do not retire an old key just because current rows have been rewrapped: older database backups still contain the older envelopes. Rewrapping cannot revoke copies of a data key already obtained by an attacker.

Local keys remain operator-controlled in self-hosted installations. Keyring buffers are cleared on destruction; JavaScript/OpenSSL memory handling is best effort, not guaranteed complete process-memory erasure. The application secret configuration itself remains present for its lifetime.

## AWS KMS

Set `RECORDING_KEY_PROVIDER=aws-kms`, `RECORDING_KMS_REGION`, and `RECORDING_KMS_KEY_ARN`. The key must be a symmetric encrypt/decrypt key addressed by its immutable key ARN. Aliases are deliberately rejected. List older permitted ARNs in `RECORDING_KMS_DECRYPT_KEY_ARNS`; envelopes cannot select arbitrary KMS keys outside this allowlist.

The official pinned AWS SDK uses workload identity or its standard credential chain. Grant only the required KMS encrypt/decrypt permissions on the configured keys. The adapter authenticates purpose, tenant, meeting, recording, and recording data-key ID using KMS EncryptionContext; it verifies the returned algorithm and key ARN. Context is not secret: KMS audit records can contain it, so use opaque IDs rather than personal data. [KMS Encrypt](https://docs.aws.amazon.com/kms/latest/APIReference/API_Encrypt.html), [KMS Decrypt](https://docs.aws.amazon.com/kms/latest/APIReference/API_Decrypt.html)

Retain a local keyring when migrating older local envelopes to KMS. Conversely, retain the KMS recovery configuration if migrating back to local keys. Switching the active provider does not itself migrate existing metadata. The operator rotation action supports both transitions. KMS credentials, plaintext data keys, and recording passwords are never stored in object metadata.

## Private S3-compatible ciphertext storage

Set `RECORDING_STORAGE=s3` plus `RECORDING_S3_BUCKET`, `RECORDING_S3_REGION`, and optionally an HTTPS `RECORDING_S3_ENDPOINT`, safe `RECORDING_S3_PREFIX`, and `RECORDING_S3_PATH_STYLE=true`. The endpoint is fixed operator configuration. Production rejects plaintext HTTP. Local tests may explicitly enable an HTTP loopback IP endpoint with `RECORDING_S3_ALLOW_LOCAL_HTTP=true`; `localhost` or arbitrary HTTP hostnames are not accepted.

Use a dedicated private bucket/prefix and least-privilege workload identity. Enable public-access blocking, versioning, and deny insecure transport in the provider policy. Paid storage requires enabled versioning; only the legacy path can use unversioned buckets. The adapter never requests a public ACL or returns a public/presigned object URL. Application-layer ciphertext remains encrypted independently of optional provider disk encryption. The code cannot prove that an operator's bucket policy is private; verify that with the actual provider before deployment.

The legacy/unbound upload path verifies complete authenticated ciphertext before starting multipart upload. Parts are at most 8 MiB; the configured object bound defaults to 64 GiB and cannot exceed that limit. Every part carries a SHA-256 checksum. Completion uses `If-None-Match: *`, so existing object keys are not overwritten. Object keys derive from the authorized context and immutable recording data-key ID. Confirm your S3-compatible provider supports conditional multipart completion and checksums. A provider that ignores those semantics is unsupported. The paid single-PUT path is described above. [S3 conditional completion](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CompleteMultipartUpload.html)

After completion, both paths read back the entire ciphertext and compare its size and SHA-256 digest before returning an immutable reference. This extra read incurs transfer cost. A lost completion acknowledgement or duplicate retry is recovered only if the existing object's bytes match exactly. Legacy multipart uploads are aborted when possible; configure a bucket lifecycle rule to abort incomplete multipart uploads because process death can prevent cleanup.

The API commits the object reference alongside encryption metadata before deleting either the raw spool or local ciphertext recovery copy. A database or upload failure leaves the row unavailable and retryable. A restart after the reference commit can finish local cleanup without re-encrypting. Paid attempts retain their own durable inventory; legacy ciphertext created before a lost database acknowledgement may remain orphaned. Reconcile legacy orphan objects against database backups before deletion. Lifecycle expiry is asynchronous and is not proof of immediate deletion.

Downloads still require the matching host session, a valid unexpired token lasting up to 24 hours within seven-day retention, and the separately emailed password. S3 downloads use the committed key, version, ETag, length, and digest, then stream per-chunk authenticated decryption directly to the response. No decrypted intermediate file is created. Complete-file integrity requires a clean stream end; earlier authenticated chunks may already have reached the authorized host when later corruption aborts the response. Disconnecting the response cancels preparation and closes the upstream object stream, including stalled reads and cancellation before the first read. The request signal also cancels a pending S3 GetObject before its response arrives.

New recordings automatically receive one download link after verified encryption completes. The host panel retrieves the link through an authenticated, non-cacheable request; the verified room email receives only its separate password. A pending email retry reuses one encrypted password, token and Message-ID. Confirmed delivery removes the wrapped password promptly; expiry, email change, host revoke, account revoke and deletion remove both envelopes and invalidate the hashes. An explicit host request can replace the current pair. Key rotation rewraps any still-live delivery envelopes with the recording key; retain old unwrap keys until rotation or expiry. SMTP/SES can duplicate a message after an ambiguous result, but such a retry never creates a second valid link.

Link creation and download admission enforce the seven-day cutoff even when the cleanup worker is unavailable. Each plaintext frame also requires a fresh shared-store check of the host session, link, expiry and recording metadata. Revocation, expiry or an unavailable store stops further frames and closes the source; already handed-off bytes cannot be recalled. Hosted starts debit the full declared file size before streaming, including retries and interrupted downloads; see [the API contract](api-contract.md). The browser streams the attachment directly without a JavaScript file-size cap. Its downloaded MP4 is plaintext and has no password protection.

The seven-day retention path atomically marks the row `deleting` and revokes download access before deleting the referenced object/version. New links and key rotations are rejected while deletion is pending. A storage outage keeps deletion retryable. Provider replicas, noncurrent versions, independent backups, and lifecycle delays require their own retention policy and restore/deletion evidence. Do not disable the S3 configuration while live rows still reference it. Existing local recordings continue using local files after S3 is enabled; there is no automatic bulk data migration.

## Recovery and deployment limits

Back up the database, key configuration/identity policy, ciphertext, and object version IDs coherently. Test restoration with both an old unrotated envelope and a newly rotated one. Keep the object bucket/prefix configuration stable across restore; metadata cannot redirect recovery to another bucket or prefix. A missing key, wrong context, changed object, or absent recovery provider fails closed.

The adapter tests cover command contracts and failure handling with SDK-boundary fakes; they do not prove AWS IAM, provider compatibility, bucket policy, regional availability, or a real KMS integration. Run an isolated S3-compatible integration and a separately authorized provider test before external use. No billable cloud calls are made by the unit tests.

The opt-in integration test is `packages/recording/test/s3.integration.test.ts`. It accepts only a loopback IP endpoint and explicit fixture credentials supplied through `TEST_S3_ENDPOINT`, `TEST_S3_ACCESS_KEY`, `TEST_S3_SECRET_KEY`, and optional `TEST_S3_REGION`. It creates and cleans up its own random private test bucket, enables versioning, uploads encrypted multipart data, verifies retry immutability, restores the committed version after an administrative overwrite, and verifies deletion cannot fall back to another version. It does not use ambient cloud credentials. With the isolated fixture running and its environment file protected and ignored by Git, run from the repository root:

```sh
node --env-file=runtime/storage-test/.env --import tsx --test packages/recording/test/s3.integration.test.ts
```

The ordinary test suite skips this provider test unless explicitly configured. A compatible emulator passing it does not establish production provider, IAM, KMS, or bucket-policy validation.

Local validation on 2026-10-04 passed this test against the isolated source-built MinIO `RELEASE.2025-10-15T17-29-55Z` fixture in `infra/minio-test.Dockerfile`. The test uses the production adapter's three-attempt SDK policy, including reconnecting when the provider closes a socket after rejecting a duplicate conditional write. The test cleaned its generated bucket and object versions. This disposable fixture is not a production storage recommendation.

Recording start, reconciliation, encryption finalization, key rotation, and retention use a PostgreSQL session advisory lock for each recording. The lock uses one reserved connection; state mutations and audit writes use that same connection. Other API processes skip busy records and reload the committed state after acquiring ownership. Process death releases ownership automatically. Stop requests persist their intent even while another process owns the recorder, so a delayed start still observes the stop.

Encryption writes a new, exclusive `<recording-id>.<attempt-id>.mprec` file and commits its attempt ID with the envelope. Paid paths persist the prepared attempt before writing; legacy paths commit its ID with the final envelope. A worker that loses its database session cannot commit further state, and its late encryption cannot overwrite the winner's output. Recovery verifies the full committed local ciphertext or object before removing the raw spool. A lost commit acknowledgement preserves both files; the next owner reloads the committed envelope and completes cleanup. Old rows without an attempt ID retain their original filename. Uncommitted legacy attempts can remain private orphan ciphertext: reconcile them against live database rows and coherent backups before operator deletion. Do not delete an apparently orphaned file while workers are running or a database commit is uncertain.

All API replicas and Egress workers must use the same shared spool and encrypted-file volumes with matching configured paths. PostgreSQL ownership does not replicate local files. Use direct PostgreSQL connections or a session-pooling proxy; transaction-pooling proxies cannot preserve advisory ownership. Stop older API workers before deploying this change because earlier versions do not participate in these locks. Storage directories must be real directories with mode `0700`; symlinked or broadly accessible directories are rejected. Completed raw input must be a regular file within `RECORDING_MAX_BYTES`. Keep the existing bounded tmpfs/encrypted ephemeral spool, swap protections, storage quotas, object lifecycle rules, and restore drills; database locks do not provide those controls.

The opt-in `apps/api/test/recording-postgres.integration.test.ts` uses two independent pools and a killed owner process against the disposable loopback `covemeet_phone_test` database. Set `RECORDING_TEST_DATABASE_URL` (or the existing `PHONE_TEST_DATABASE_URL`) to that fixture. It checks live contention, process-death lock release, database-connection loss during encryption, rejection of the stale worker's commit, and successful decryption of the surviving output. It makes no provider calls.
